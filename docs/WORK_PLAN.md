# תוכנית עבודה — בנייה מחדש של מערכת ההזמנות

**מסמך נלווה ל-[PRD.md](PRD.md)** — ה-PRD מגדיר *מה* המערכת עושה; המסמך הזה מגדיר *באיזה סדר בונים* ו*מה בודקים בסוף כל שלב* לפני שממשיכים הלאה.

---

## עקרונות עבודה

1. **בסוף כל שלב האפליקציה עובדת ונראית זהה** — אין שלב שמשאיר את המערכת שבורה או "חצי בנויה" מבחינת המשתמש.
2. **כל שלב מבטל את מה שהוא מחליף** — לא משאירים מנגנון ישן וחדש זה לצד זה "ליתר ביטחון". מה שהוחלף נמחק באותו שלב.
3. **שער מעבר (Gate):** לא עוברים לשלב הבא לפני שכל בדיקות האימות של השלב הנוכחי עוברות. אם בדיקה נכשלת — מתקנים לפני שממשיכים.
4. **בדיקות רגרסיה חוזרות בכל שלב** (רשימה בסוף המסמך) — בנוסף לבדיקות הייעודיות של השלב.
5. **סביבת פיתוח:** Supabase מקומי (`supabase start`) עם נתוני בדיקה. הנתונים האמיתיים (קטלוג, לקוחות, מחירים) מוזנים רק בהקמת סביבת הייצור — שום נתון מהאב-טיפוס לא עובר (ראו PRD §10).

### מי מבצע את הבדיקות

רוב הבדיקות במסמך זה מבוצעות **על ידי Claude, אוטומטית**, ומדווחות לך כתוצאה. הבדיקות שדורשות אותך מסומנות ב-👤.

**מה Claude מריץ לבד:**
- כל בדיקות ה-DB: מיגרציות, סכימה, פונקציות, jobs — דרך `supabase` CLI ו-SQL.
- **בדיקות אבטחה (RLS)** — קריאות API ישירות עם JWT של כל משתמש בדיקה, כדי לוודא שההגנה בשרת ולא רק ב-UI.
- **בדיקות UI מקצה לקצה** — הרצת האפליקציה בדפדפן, לחיצות, מילוי טפסים, ניווט, צילומי מסך, קריאת שגיאות קונסול.
- **השוואה ויזואלית** — צילום כל מסך במובייל (393px) ובדסקטופ והשוואה מול האב-טיפוס.
- **בדיקות תלויות-זמן** — מימוש קבועות, מעבר ל-completed, מחיקת טיוטות שפגו: על ידי הזרקת נתונים עם תאריכים מתאימים והרצת ה-jobs ידנית (לא צריך לחכות לזמן אמת).
- **Realtime** — פתיחת שני טאבים במקביל, אישור הזמנה באחד ואימות שהיא מופיעה בשני.
- ניקוי קוד: grep לשאריות, בדיקת imports יתומים, build, lint, typecheck.

**מה דורש אותך (👤) — סה"כ 9 בדיקות בלבד:**

## שלב 0 — תשתית (ללא שינוי UI)

### מטרה
בסיס טכני מוכן: Supabase מקומי עם הסכימה המלאה, PWA, ושכבת API מופרדת — בלי לגעת עדיין בהתנהגות האפליקציה.

### משימות
- **ניתוק מלא מ-Lovable (קודם כול — הבנייה תלויה בו כרגע):**
  - כתיבת `vite.config.ts` עצמאי במקום `@lovable.dev/vite-tanstack-config`. החבילה הזו מספקת
    כיום בשקט את כל תשתית הבנייה: tanstackStart, viteReact, tailwindcss, tsConfigPaths, nitro,
    הזרקת משתני סביבה, alias `@/`, dedupe ותוספי שגיאות. צריך להגדיר את כולם מפורשות.
  - **קריטי:** יעד ה-nitro בחבילה של Lovable הוא **cloudflare** כברירת מחדל. יש להחליף ל-**vercel**
    (ראו שלב 7) — אחרת הפריסה לא תעבוד.
  - מחיקת `src/lib/lovable-error-reporting.ts` והשימוש בו ב-`__root.tsx` (קוד מת מחוץ ל-Lovable),
    `AGENTS.md`, תיקיית `.lovable/`, והחלפת `README.md` בתוכן אמיתי של הפרויקט.
  - הסרת התלות מ-`package.json`.
- ~~חיבור למאגר GitHub החדש~~ — **בוצע כבר** (ה-`origin` מצביע על `gilitzruya/shney-haofim-bakery` וה-commit הראשון נדחף).
- התקנת Supabase CLI והרצת סטאק מקומי (`supabase start`).
- כתיבת כל המיגרציות: enums, כל הטבלאות מ-PRD §9 (categories, products, customers, customer_contacts, app_users, customer_prices, orders, order_lines, recurring_orders, recurring_order_lines, cutoff_rules, cutoff_exceptions, documents, bakery_settings), אינדקסים, ופונקציית `fn_cutoff_at`.
- כתיבת כל מדיניות ה-RLS (PRD §9) — גם אם עדיין אין UI שמפעיל אותן.
- Seed לנתוני בדיקה (קטלוג בדיקה קטן, משתמשי הבדיקה שלמעלה) — **מסומן בבירור כ-seed פיתוח בלבד**.
- יצירת טיפוסי TypeScript מהסכימה (`supabase gen types`) + חיבורם לפרויקט.
- הקמת שכבת `src/lib/api/` עם supabase-js client מוגדר (עדיין לא בשימוש על ידי המסכים).
- PWA: manifest (שם, אייקונים, צבעים), service worker בסיסי, רכיב חלון קופץ להתקנה.

### חיבור Vercel Preview מוקדם — כדי שבעל המאפייה יראה התקדמות תוך כדי, לא רק בסוף
פעולה **חד-פעמית**, לא משימה שחוזרת בכל שלב: ברגע שריפו ה-GitHub מחובר לפרויקט Vercel, **כל
push** (גם ל-branch, לא רק ל-main) מקבל אוטומטית קישור Preview חי משלו — מכאן והלאה, בלי
מאמץ נוסף בכל שלב.

הבעיה: Preview רץ באינטרנט ולא יכול להתחבר ל-Supabase המקומי (Docker) שרץ על המחשב. לכן:
- מקימים כבר עכשיו **פרויקט Supabase מאוחסן** (לא רק מקומי) — נגיש דרך האינטרנט, גם אם ריק/דל.
- מריצים עליו את **אותן מיגרציות** בדיוק כמו על המקומי.
- מחברים את פרויקט ה-Vercel לריפו, עם משתני הסביבה מצביעים על ה-Supabase המאוחסן הזה (המפתח
  הציבורי בלבד — לא `service_role`).
- **זה לא סביבה זמנית שנזרקת** — זה בדיוק אותו פרויקט Supabase שיתקשח לייצור אמיתי בשלב 7
  (נתוני אמת, Twilio, דומיין). אין כפילות עבודה, רק הקמה מוקדמת יותר.
- הפיתוח היומיומי ממשיך על Supabase המקומי (מהיר, לא תלוי אינטרנט) — ה-Preview המאוחסן
  משמש רק לתצוגה/פידבק, לא לעבודת הפיתוח השוטפת.

### בדיקות בסוף השלב

## שלב 1 — אימות ושלד הרשאות

### מטרה
כניסה בטלפון + קוד SMS, הפרדת תפקידים מלאה: לקוח רואה רק את צד הלקוח, מנהל נכנס לניהול.

### משימות
- הפעלת Supabase Auth בערוץ phone/OTP (בפיתוח: OTP בדוי של Supabase מקומי; בייצור: Twilio).
- מסך כניסה חדש (הזנת טלפון ← הזנת קוד) בשפה העיצובית הקיימת.
- לוגיקת `app_users`: אחרי אימות, שליפת role + customer_id; ניתוב לפי תפקיד (customer ← צד לקוח, admin ← `/admin`).
- חסימת כל המסכים למשתמש לא מחובר; חסימת `/admin/*` ללקוח — ב-routing **וגם** ב-RLS.
- עדכון מודאל "שליחת פרטי התחברות בוואטסאפ": בלי סיסמה זמנית, עם הנחיית OTP (החלטה 8).
- יצירת משתמש/הרשאה אוטומטית כשמסמנים לאיש קשר "יש לו גישה" (בסיס — ההרחבה המלאה לריבוי אנשי קשר בשלב 3).

### בדיקות בסוף השלב
- [ ] כניסה מלאה עובדת: טלפון ← קוד ← נכנסים. קוד שגוי נדחה עם הודעה ברורה. *(בפיתוח: OTP מדומה של Supabase מקומי. שליחת SMS אמיתית נבדקת בשלב 7.)*
- [ ] משתמש לא מחובר שמנסה להגיע לכל URL (כולל עמוק, כולל `/admin`) מגיע למסך הכניסה.
- [ ] לקוח א׳ שמקליד `/admin` ידנית בכתובת — נחסם (לא רק תפריט מוסתר).
- [ ] קריאת API ישירה (curl עם ה-JWT של לקוח א׳) לטבלת admin — נחסמת ב-RLS. **בדיקה קריטית: ההגנה היא בשרת, לא רק ב-UI.**
- [ ] מנהל נכנס ומגיע ישירות לפאנל הניהול.
- [ ] סגירת דפדפן ופתיחה מחדש — עדיין מחוברים (session נשמר), בלי לבקש קוד שוב.
- [ ] התנתקות יזומה ← חוזרים למסך כניסה, וכניסה חוזרת דורשת קוד חדש.
- [ ] הודעת הוואטסאפ החדשה לא מכילה סיסמה, כן מכילה את הקישור וההנחיה (בדיקת תוכן הקישור והטקסט).
- [ ] הקישור בתוך ההודעה הוא כתובת **Preview אמיתית**, לא `localhost` — הקישור נבנה בקוד מ-`window.location.origin`, כך שאם פותחים את מסך השליחה מהסביבה המקומית, ההודעה תכיל קישור שהלקוח לא יכול לפתוח אצלו. יש לבדוק זאת מתוך ה-Preview, לא מקומית.
- [ ] 👤 שליחה אמיתית של ההודעה בוואטסאפ ללקוח בדיקה **דרך ה-Preview** — נפתחת, נשלחת, והקישור שבתוכה נפתח בהצלחה במכשיר של הנמען.
- [ ] איש הקשר השני של לקוח א׳ נכנס עם הטלפון שלו ורואה את אותם נתונים של לקוח א׳.

## שלב 2 — קטלוג מ-DB

### מטרה
הקטלוג (קטגוריות, מוצרים, תמונות, זמינות, סדר) חי ב-Supabase; מסכי ניהול המוצרים כותבים ל-DB. צד הלקוח קורא מה-DB.

### משימות
- החלפת מקור הקטלוג: hooks חדשים (`useCatalog` וכו') על TanStack Query במקום הקטלוג שב-store; מחיקת עותק ה-runtime (`applyRuntimeCatalog`, `findProduct` הגלובלי) לטובת גישה דרך ה-hooks.
- העלאת תמונות ל-Supabase Storage (במקום data URL ב-localStorage); מחיקת `image-upload.ts` בהתאמה או עדכונו להעלאה ל-Storage.
- מסכי `/admin/products`: יצירה/עריכה/מחיקה/שינוי שם/סדר גרירה/זמינות — הכול מול DB.
- דיאלוג אישור לפני מחיקת מוצר; מחיקה = soft delete (`deleted_at`).
- RLS: כתיבת קטלוג לאדמין בלבד.

### בדיקות בסוף השלב
- [ ] הקטלוג בצד הלקוח נטען מה-DB ונראה **פיקסל-זהה** לקודם (קטגוריות, כרטיסי מוצר, טאבים, חיפוש).
- [ ] מנהל משנה מחיר/שם/זמינות ← רענון בצד הלקוח מציג את השינוי.
- [ ] גרירת סדר קטגוריות בניהול משנה את סדר התצוגה בקטלוג הלקוח.
- [ ] העלאת תמונת מוצר נשמרת ב-Storage ומוצגת בקטלוג; החלפה והסרה עובדות.
- [ ] מחיקת מוצר מציגה דיאלוג אישור; אחרי אישור המוצר נעלם מהקטלוג אבל השורה נשארת ב-DB עם `deleted_at` (soft delete).
- [ ] מוצר "לא זמין" מוצג בשקיפות ולא ניתן להוספה — כמו קודם.
- [ ] מחיקת קטגוריה אפשרית רק כשהיא ריקה.
- [ ] לקוח (JWT של לקוח א׳) שמנסה לכתוב לטבלת products דרך ה-API — נחסם.
- [ ] כמויות/צעדים (יחידה מול ק"ג, מינימום, quickAdd) מתנהגים בדיוק כמו קודם.

## שלב 3 — הזמנות ולקוחות

### מטרה
לב המערכת: זרימת ההזמנה המלאה מול DB עם כל כללי ה-PRD — נעילה אחרי אישור, ריבוי הזמנות, מחירי לקוח, טיוטות מתמשכות; וניהול לקוחות מלא כולל ריבוי אנשי קשר.

### משימות
- טבלאות orders/order_lines חיות: טיוטה נשמרת ב-DB (autosave), אישור דרך `rpc_confirm_order` (ולידציה + snapshot מחירים).
- זרימת הלקוח לפי PRD §3: שאלת העתקה מודעת-שישי ← ישירות לסיכום (החלטה 11), בחירת תאריך+סבב לפי הרשאה (החלטה 3), הערה למאפייה נשמרת, נעילה מוחלטת אחרי אישור (החלטה 1), ריבוי הזמנות לאותו יום+סבב (החלטה 2).
- מסך פרטי הזמנה ללקוח: בלי עריכה/ביטול להזמנה מאושרת; "שכפול כהזמנה חדשה" נשאר.
- צד ניהול: הזמנות ליום, פירוט, עריכה/ביטול/שחזור עד completed, יצירת הזמנה בשם לקוח.
- לקוחות: CRUD מלא, רשימת אנשי קשר עם גישה פר-איש-קשר (החלטה 20), מחירים מיוחדים, חסימה (כולל התנהגות צד לקוח — החלטה 13), "פרטי העסק" לתצוגה בלבד (החלטה 17).
- מחיר הלקוח מוצג בצד הלקוח (קטלוג + סיכום + פרטי הזמנה).
- הפעלת `job_close_completed_orders` (אוטומציה ל-completed) ו-`job_expire_stale_drafts` (מחיקת טיוטות שפגו — החלטה 15, החלטה 9).
- מחיקת החלקים המקבילים מה-store הישן (orders, adminOrders, customers, business, draft) — צד ההזמנות עובר כולו ל-DB.

### בדיקות בסוף השלב
**זרימת לקוח:**
- [ ] הזמנה מלאה מקצה לקצה: קטלוג ← סל ← סיכום ← תאריך ← אישור ← מופיעה ב"ההזמנות שלי" וב-DB עם snapshot מחירים.
- [ ] לקוח א׳ (יש לו מחיר מיוחד) רואה את המחיר **שלו** בקטלוג ובסיכום; שורת ההזמנה נשמרת עם המחיר הזה. לקוח ב׳ רואה מחיר קטלוג.
- [ ] לקוח א׳ נשאל על סבב בשלב התאריך; לקוח ב׳ לא נשאל ומקבל סבב ראשון.
- [ ] אחרי אישור: אין כפתורי עריכה/ביטול; מוצגת הודעת "לשינויים יש לפנות למאפייה". גם ניסיון עדכון ישיר ב-API עם JWT של הלקוח — נחסם (RLS).
- [ ] יצירת הזמנה שנייה לאותו תאריך+סבב — עוברת בלי אזהרת קונפליקט חוסמת.
- [ ] שאלת ההעתקה: הזמנה לתאריך יום שישי מציעה את הזמנת שישי האחרונה; לתאריך אחר — את האחרונה שאינה שישי; אחרי "כן" מגיעים ישירות לסיכום עם הפריטים; "הוספת מוצרים" מהסיכום מוביל לקטלוג.
- [ ] "הערה למאפייה" שמולאה בסיכום מופיעה בפירוט ההזמנה בניהול.
- [ ] טיוטה שורדת: סגירת דפדפן, מעבר בין מסכים, כניסה ממכשיר אחר של אותו משתמש. טיוטה עם תאריך שעבר סגירה — נמחקת אוטומטית.
- [ ] ניסיון אישור אחרי שעת הסגירה נדחה עם המודאל הקיים (גם אם עוקפים את ה-UI — ה-RPC דוחה).
- [ ] לקוח ג׳ (חסום) נכנס, רואה היסטוריה, לא רואה כפתורי הזמנה חדשה, מקבל הסבר.
- [ ] הזמנה שתאריכה עבר הופכת אוטומטית ל"הושלמה" ועוברת לטאב היסטוריה.

**צד ניהול:**
- [ ] ההזמנה שאושרה על ידי הלקוח מופיעה מיידית במסך ההזמנות של הניהול לאותו תאריך, בסבב הנכון.
- [ ] מנהל עורך כמויות/מוסיף מוצרים/מבטל/משחזר — עובד עד completed; אחרי completed הכול נעול (גם למנהל).
- [ ] יצירת הזמנה בשם לקוח ב׳ — הסבבים מוגבלים להרשאותיו, המחירים לפי המחירון שלו, וההזמנה מופיעה אצל הלקוח.
- [ ] כרטיס לקוח: הוספת איש קשר שני, סימון "יש לו גישה", שליחת הזמנה אישית — ואיש הקשר החדש מצליח להיכנס.
- [ ] חסימת לקוח מהניהול נכנסת לתוקף מיידית (הלקוח החסום לא יכול לאשר הזמנה — גם ב-RPC).
- [ ] "פרטי העסק" בצד הלקוח: תצוגה בלבד, בלי כפתור שמירה; עריכת הפרטים בכרטיס הלקוח בניהול משתקפת אצל הלקוח.
- [ ] סה"כ בשורת הזמנה ישנה לא משתנה כשמשנים מחיר בקטלוג (בדיקת snapshot).

## שלב 4 — הזמנות קבועות + מנוע מימוש

### מטרה
הזמנות קבועות במודל הדו-שכבתי המלא (PRD 2.4): תצוגה וירטואלית מיידית בכל דוח עתידי, מימוש אוטומטי ב-cutoff, מימוש מיידי בעריכה חד-פעמית של הניהול.

### משימות
- טבלאות recurring_orders/lines חיות; ישות אחת ללקוח ולניהול (איחוד `adminRecurring`).
- מסכי הלקוח: יצירה (עם בחירת סבב מתוקנת — החלטה 3), עריכה, השהיה/הפעלה, ביטול. **הסרת "עדכון חד-פעמי"** (החלטה 5).
- הודעת "השינוי יחול מהאספקה הבאה בתאריך X" כשעורכים אחרי שהאספקה הקרובה ננעלה.
- `fn_recurring_occurrences` + שילוב וירטואלי בכל מסכי/דוחות התאריך בניהול, עם תווית "קבועה".
- `rpc_materialize_recurring_occurrence` + `job_close_upcoming_recurring`.
- עריכה/ביטול של מופע וירטואלי מהניהול ← ממש אותו מיידית.
- אכיפת ייחודיות: קבועה פעילה אחת ללקוח+יום+סבב.
- מחיקת `adminRecurring`, `recurring` מה-store הישן ו-`startOneTimeUpdate`/מצב `onetime`.

### בדיקות בסוף השלב
- [ ] לקוח יוצר הזמנה קבועה לימי שלישי ← **מיד** מופיעה (עם תווית "קבועה") בדוח של יום שלישי הקרוב וגם בעוד שבועיים, בלי לחכות לשום job.
- [ ] הלקוח מעדכן כמות בתבנית ← כל התצוגות העתידיות הווירטואליות מתעדכנות מיידית.
- [ ] השהיה ← נעלמת מכל התאריכים העתידיים; הפעלה מחדש ← חוזרת.
- [ ] הגיע ה-cutoff של יום שלישי (בבדיקה: מזיזים שעון/מריצים job ידנית) ← נוצרת שורת `order` אמיתית עם snapshot; מהרגע הזה עריכת התבנית לא משנה אותה.
- [ ] עריכת תבנית אחרי שהאספקה הקרובה ננעלה ← מוצגת הודעת "יחול מ-X" עם התאריך הנכון.
- [ ] מנהל עורך מופע וירטואלי ליום ספציפי ← נוצרת רשומה אמיתית עם השינוי; התבנית לא השתנתה; שאר הימים נשארו וירטואליים ולפי התבנית.
- [ ] מנהל מבטל מופע ליום ספציפי ← נוצרת רשומה מבוטלת; היום הזה לא מופיע בדוחות; שאר הימים לא הושפעו.
- [ ] ניסיון ליצור קבועה שנייה לאותו לקוח+יום+סבב — נדחה עם ההודעה הקיימת.
- [ ] קבועה שנוצרה בשם לקוח מהניהול מופיעה אצל הלקוח וזהה בהתנהגות.
- [ ] אין יותר כפתור "עדכון חד-פעמי" בצד הלקוח.
- [ ] מופע ממומש מופיע גם ב"הזמנות שנכנסו" ומתנהג כהזמנה רגילה (עריכה, תעודה, completed).

## שלב 5 — כללי סגירה, דוחות, מסמכים ועדכון חי

השלמת צד הניהול: ניהול שעות סגירה מה-DB, דוחות מלאים (כולל וירטואליים), תעודות משלוח, ועדכון Realtime בדף הבית.

### משימות
- מסך `/admin/cutoff` מול cutoff_rules/exceptions ב-DB; כל חישובי הסגירה במערכת עוברים ל-`fn_cutoff_at`.
- טקסט ה-cutoff ללקוח הופך דינמי לפי הכלל בפועל (PRD §11).
- דוחות ייצור/חלוקה כשאילתות אגרגציה מה-DB, כולל מופעים וירטואליים, לכל תאריך עתידי; גיליונות ההדפסה נשארים זהים.

- דף הבית: Supabase Realtime על orders + כפתור רענון ידני + רענון ב-focus/reconnect (החלטה 21).

## שלב 7 — עלייה לאוויר (הקשחת הפרודקשן)

### מטרה
המערכת רצה בייצור על דומיין אמיתי, עם נתוני אמת, ובעל המאפייה עובד איתה בפועל.

**הערה:** Vercel והפרויקט המאוחסן ב-Supabase **כבר קיימים** מאז סוף שלב 0 (שם הוקמו כדי
לאפשר קישורי Preview לאורך כל הדרך) — השלב הזה הוא **הקשחה** של מה שכבר יש (נתוני אמת,
Twilio, דומיין, גיבויים, pg_cron), לא הקמה מאפס.

### החלטה טכנית: איפה רצות המשימות המתוזמנות
ה-jobs (`job_close_upcoming_recurring`, `job_close_completed_orders`, `job_expire_stale_drafts`) ירוצו ב-**pg_cron בתוך Supabase**, ולא ב-Vercel Cron. הסיבות:
1. **עצמאות מהאתר** — המשימות האלה קריטיות (מימוש הזמנות קבועות, נעילת הזמנות). הן חייבות לרוץ גם אם הפריסה ב-Vercel נכשלה או שהאתר מושבת.
2. **תדירות** — במסלול החינמי של Vercel, Cron מוגבל להרצה יומית אחת; אנחנו צריכים בדיקה תכופה יותר (מועדי סגירה משתנים לפי יום). ב-pg_cron אין הגבלה כזו.
3. **קרבה לנתונים** — המשימות הן SQL טהור על הטבלאות; אין סיבה שיעברו דרך HTTP.

### משימות
- **Supabase:** על הפרויקט המאוחסן הקיים (מאז שלב 0) — הפעלת pg_cron ורישום שלושת ה-jobs, הגדרת גיבויים אוטומטיים.
- **Twilio:** חשבון, מספר שולח, חיבורו ל-Supabase Auth לערוץ SMS (עד עכשיו ה-Preview עבד בלי SMS אמיתי).
- **Vercel:** קידום ה-deployment הקיים ל-production (במקום preview-only), חיבור דומיין.
- **משתני סביבה:** כתובת Supabase + המפתח הציבורי (publishable) בצד הלקוח. **מפתח ה-service_role לעולם לא נכנס ל-bundle של הדפדפן** — רק בסודות השרת/Edge Functions.
- **דומיין:** חיבור הדומיין של המאפייה ל-Vercel, כולל HTTPS.
- **Supabase Auth:** הוספת דומיין הייצור ל-Redirect URLs ול-Allowed Origins.
- **הזנת נתוני אמת:** הקטלוג האמיתי (מוצרים, קודים, מחירים, תמונות), הלקוחות ואנשי הקשר שלהם, מחירים מיוחדים, כללי שעות הסגירה, ושורות המנהלים ב-`app_users`.

### בדיקות בסוף השלב
- [ ] 👤 **קבלת SMS אמיתי** — כניסה עם הטלפון שלך לאתר הייצור, קבלת הקוד, כניסה מוצלחת.
- [ ] 👤 **אימות נתוני האמת** — מעבר על הקטלוג בייצור ואישור שכל מוצר, קוד ומחיר נכונים.
- [ ] 👤 **חיבור הדומיין** — האתר עולה בכתובת הנכונה עם HTTPS תקין.
- [ ] 👤 **התקנת ה-PWA מהדומיין האמיתי** בטלפון שלך ושל לקוח בדיקה.
- [ ] הפריסה ב-Vercel מצליחה; אין שגיאות build; האתר נטען.
- [ ] **בדיקת אבטחה קריטית:** סריקת ה-bundle שנשלח לדפדפן — מפתח ה-service_role **לא** מופיע בו.
